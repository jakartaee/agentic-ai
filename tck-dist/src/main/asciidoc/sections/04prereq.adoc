== Prerequisites

=== Software To Install

. **JDK** — Java SE {JavaVersion} or later, for both the Test Client and the Test Server.
. **Maven** — Apache Maven 3.9.0 or later.
. **A Jakarta EE runtime** — Jakarta EE 10 or later, with your {APILongName} implementation installed. Any profile that provides CDI and Jakarta JSON Binding suffices.
. **An Arquillian container adapter** for that runtime.

=== Testing Frameworks

The TCK is built on three frameworks. Knowing how they interact helps when setting up the runner.

. **{TCKTestPlatform}** (5.11 or later) — the entry point for every test.
. **Arquillian** (1.10 or later, with the Arquillian Jakarta integration) — deploys each test's archive to the Test Server and runs the test inside it. You must configure an https://arquillian.org/guides/developing_a_container_adapter/[Arquillian adapter] for your runtime. The adapter must report a failed deployment with a `jakarta.enterprise.inject.spi.DeploymentException` in the exception chain, because the deployment-error tests assert on that type with `@ShouldThrowException`; adapters that pass the CDI TCK already do.
. **Jakarta TCK signature test engine** (version {SigPluginVersion} exactly, coordinates `{SigPluginGAV}`) — verifies that the `{APIPackage}` API the Test Server provides matches the signature file recorded for this release. It is a transitive dependency of the TCK jar, and the signature test carries it into its own deployment; no action is needed. An exact version is required because signature test tools differ in small ways.

=== What the TCK supplies inside each deployment

The TCK jar registers an Arquillian `ApplicationArchiveProcessor` through `META-INF/services`.
It adds to every test archive one CDI bean the tests inject, `ee.jakarta.tck.ai.agent.framework.ExecutionTraceRecorder`, which records the order in which workflow phases run and the values they receive.

The TCK deploys no `LargeLanguageModel`.
The bean the agents under test receive is the implementation's own facade, and the TCK verifies it: placeholder substitution, JSON Binding conversion, exception mapping and conversational state are all asserted against the implementation.
For those tests to be deterministic, the model behind the facade must behave as <<Additional Certification Requirements>> specifies during the TCK run.
