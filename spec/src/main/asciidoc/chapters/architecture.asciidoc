== Architecture

This chapter provides an architectural overview of Jakarta Agentic AI,
describing how agents are structured, how they integrate with Jakarta EE,
and the key design patterns.

=== Agent Architecture

An agent in Jakarta Agentic AI is a CDI bean that orchestrates a flexible
workflow. Workflows always begin with a trigger and may include any
combination of the following phases:

1. **Trigger Phase** (required): Detects an event or condition that
                                 initiates the workflow
2. **Decision Phases** (optional): Analyze workflow state and determine 
                                   whether to proceed
3. **Action Phases** (optional): Execute operations as part of the workflow
4. **Outcome Phase** (optional): Produces the final result of the workflow

**Phase Flexibility**: Decisions and actions can be intermixed in any sequence,
                       allowing agents to implement simple linear workflows or
                       complex conditional branching patterns.

Additionally, agents may define:

- **Exception Handling**: Methods to handle errors that occur during workflow
                          execution

==== Agent as CDI Bean

Every agent is a CDI bean annotated with `@Agent`. This design provides:

- **Dependency Injection**: Agents can inject other CDI beans, Jakarta EE
                            resources, and services
- **Interceptors**: Standard CDI interceptors can be applied to agent methods
- **Scoping**: Agents can be `@WorkflowScoped` or `@ApplicationScoped`
- **Events**: Agents observe CDI events
- **Lifecycle Management**: CDI manages agent instantiation and destruction

[source,java]
----
@Agent
@ApplicationScoped
public class MonitoringAgent {

    @Inject
    private LargeLanguageModel llm;

    @Inject
    private EventLogger logger;

    @Trigger
    public void onSystemAlert(Alert alert) {
        // Triggered by external event
    }

    @Decision
    public boolean shouldEscalate(Alert alert) {
        // Use LLM to decide if escalation is needed
        String analysis = llm.query("Should this alert be escalated?", alert);
        return analysis.toLowerCase().contains("yes");
    }

    @Action
    public void escalateAlert(Alert alert) {
        // Execute escalation action
        logger.logEscalation(alert);
    }
}
----

=== Workflow Model

The workflow model in Jakarta Agentic AI is built on a foundation of annotated
methods that serve as semantic building blocks. Annotations (`@Trigger`,
`@Decision`, `@Action`, `@Outcome`) define the basic vocabulary of an agent's
workflow—marking methods that trigger workflows, make decisions, perform 
actions, and produce outcomes.

In the current release (v1.0), the runtime orchestrates these annotated methods
using a sequential execution model: the trigger fires, followed by any 
combination of zero or more decisions and actions in declaration order,
optionally concluding with an outcome. This straightforward model provides a 
clear pattern for developing agents.

**Future Direction**: A programmatic workflow API will be introduced in
subsequent releases to enable dynamic workflow composition and runtime
modification. The workflow API will wire together the annotated methods (the 
basic building blocks) into sophisticated, potentially complex control flows
that can be modified at runtime. This will unlock powerful capabilities such as
dynamic decision routing, conditional action execution, and workflows that
adapt based on agent state or LLM interactions. The initial agent workflow
could be defined or loaded from storage in a `@PostConstruct` method and 
placed into storage in a `@PreDestroy` method.

[[workflow-model]]
==== Workflow Execution (Current Release)

In this release, workflows execute sequentially in declaration order:

1. **Trigger** invoked with the event
2. **Decisions and Actions** execute in declaration order, intermixed as defined
3. **Decisions** control flow: `true`/non-null continues, `false`/`null` terminates
4. **Outcome** invoked if workflow completes without early termination

Exception handlers (`@HandleException`) execute if exceptions occur.

**Phase Requirements**:
- `@Trigger`: Required (exactly one per agent)
- `@Decision`: Optional (zero or more per agent)
- `@Action`: Optional (zero or more per agent)
- `@Outcome`: Optional (zero or one per agent)

See the xref:agent-lifecycle[Agent Lifecycle] chapter for detailed semantics of each annotation,
and the xref:workflow-orchestration[Workflow Orchestration] chapter for execution flow details.

==== Jakarta EE Service Integration

Agents can leverage Jakarta EE services:

**Data Access Services**:
- **Jakarta Persistence**: Access relational databases
- **Jakarta Data**: High-level data access with repositories
- **Jakarta NoSQL**: Access non-relational databases

**Transactional Operations**:
- **Jakarta Transactions**: Transactional agent operations across data sources

**Data Serialization**:
- **Jakarta JSON Binding**: JSON serialization for LLM interactions 
                            (required by `LargeLanguageModel`)

**Messaging & Integration**:
- **Jakarta Messaging**: Publish and consume messages from message brokers 
                         (future trigger source)

**Asynchronous Operations**:
- **Jakarta Concurrency**: Managed executors for asynchronous tasks within
                           agent logic

[source,java]
----
@Agent
public class DataIntegratedAgent {

    @Inject
    private EntityManager entityManager;  // Jakarta Persistence

    @Inject
    private CustomerRepository customerRepo;  // Jakarta Data

    @Inject
    @Inject("mongodb")
    private Template mongoTemplate;  // Jakarta NoSQL

    @Inject
    private ManagedExecutorService executor;  // Jakarta Concurrency

    @Action
    @Transactional  // Jakarta Transactions
    public void processCustomerData(CustomerId id) {
        // Use JPA
        Customer customer = entityManager.find(Customer.class, id);
        
        // Use Jakarta Data repository
        List<Order> orders = customerRepo.findOrdersByCustomerId(id);
        
        // Use NoSQL for unstructured data
        mongoTemplate.insert(new AnalyticsEvent(customer, orders));
        
        // Async processing
        executor.submit(() -> generateReport(customer, orders));
    }
}
----

=== LLM Facade Pattern

A key architectural decision in Jakarta Agentic AI is the use of a facade
pattern for LLM access. The `LargeLanguageModel` interface provides a simple,
consistent API while allowing vendors to integrate any LLM backend.

==== Facade Benefits

**Abstraction**: Applications depend on the facade, not specific LLM
                 implementations

**Vendor Flexibility**: Implementations can integrate any LLM provider or
                        implementation

**Unwrapping**: The `unwrap()` method allows accessing vendor-specific APIs
when needed, following Jakarta Persistence's `EntityManager.unwrap()` pattern

**Evolution**: LLM technologies evolve rapidly; the facade insulates
               applications from these changes

==== JSON Binding Integration

The `LargeLanguageModel` facade leverages Jakarta JSON Binding to enable
type-safe LLM interactions. Implementations must use Jakarta JSON Binding for 
serialization and deserialization.

**Prompt Parameter Serialization**:
- When domain objects are passed as parameters to the varargs `query(...)`
  methods, implementations serialize them to JSON using Jakarta JSON Binding
- The exact token `{}` in the prompt acts as a positional placeholder,
  similar to well-known logger APIs
- Parameters are substituted in declaration order
- When the prompt contains one or more `{}` placeholders, the number of
  supplied parameters must exactly match the number of placeholders
- When the prompt contains no placeholder, at most one supplied parameter may
  be provided to the LLM as structured context
- This allows agents to pass complex objects (transactions, events, entities)
  directly to LLM queries without manual serialization

**Response Type Conversion**:
- When a `resultType` is specified, implementations deserialize the LLM's
  response from JSON to the requested type using Jakarta JSON Binding
- This enables type-safe responses without manual parsing
- Implementations must throw `IllegalArgumentException` if type conversion
  fails

[source,java]
----
@Decision
public FraudAnalysis analyzeFraud(BankTransaction transaction) {
    // transaction is serialized to JSON automatically
    // Response is deserialized to FraudAnalysis automatically
    FraudAnalysis analysis = llm.query(
        "Analyze this transaction for fraud patterns and return JSON",
        FraudAnalysis.class,
        transaction
    );
    return analysis;
}
----

**Benefits**:
- Type safety without manual JSON handling
- Consistent serialization behavior across implementations
- Portability through standard Jakarta JSON Binding
- LLM-friendly structured data exchange

=== Design Patterns

Jakarta Agentic AI employs several design patterns familiar to Jakarta EE
developers:

==== Annotation-Driven Development

Like Jakarta REST, Servlet, and Batch, Jakarta Agentic AI uses annotations to
declaratively define behavior. This reduces boilerplate and makes code more
readable.

==== Convention over Configuration

Sensible defaults minimize configuration:

- Default scope is `@WorkflowScoped`
- Workflow phases execute in method declaration order
- Parameter injection resolves based on type

==== Declarative Workflow Pattern

Agents declare their workflow phases using annotations on methods. The runtime
orchestrates execution based on method declaration order, starting with the
trigger and proceeding through any combination of decisions and actions,
optionally ending with an outcome.

=== Threading and Concurrency

Jakarta Agentic AI workflow phases execute sequentially:

- **Sequential Phases**: Annotated methods (@Trigger, @Decision, @Action,
                         @Outcome) execute in declaration order
- **Flexible Composition**: Agents can define any combination of decisions
                            and actions, intermixed as needed
- **Thread Safety**: Agents using `@WorkflowScoped` typically execute within a
                     single thread per workflow execution. `@ApplicationScoped`
                     agents must take thread-safety into account as they may
                     handle multiple concurrent workflow invocations.

For details on error handling, exception recovery, and workflow termination, see
the xref:workflow-error-handling-recovery[Error Handling and Recovery] section in the Workflow Orchestration chapter.
