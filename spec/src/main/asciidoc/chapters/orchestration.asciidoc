[[workflow-orchestration]]
== Workflow Orchestration

This chapter describes how workflows are orchestrated in Jakarta Agentic AI, including
parameter injection and execution flow control.

[[workflow-parameter-injection]]
=== Parameter Injection

Jakarta Agentic AI provides automatic parameter injection for workflow methods. Parameters
are resolved based on their type and the current workflow state.

==== Injection Resolution Rules

When a workflow method is invoked, the runtime resolves parameters in the following order:

1. **Trigger Event**: If the parameter type matches the trigger event type
2. **Previous Phase Results**: If the parameter type matches a stored result
3. **LargeLanguageModel**: If the parameter type is `LargeLanguageModel`
4. **CDI Injection**: If the parameter is a CDI bean

==== Jakarta Validation Constraints

Parameters can declare Jakarta Validation constraints using annotations such as `@Valid`, 
`@NotNull`, `@NotEmpty`, `@Size`, `@Pattern`, `@Email`, and custom constraint annotations. 
Validation occurs before parameter injection and workflow method invocation. If validation fails, 
a `ConstraintViolationException` is raised and can be handled by `@HandleException` methods 
or propagated to the container.

===== ConstraintViolationException

`ConstraintViolationException` is a runtime exception thrown when Jakarta Validation constraints 
on method parameters are violated. As a runtime exception, it does not require explicit handling 
but can be caught by `@HandleException` methods in agent workflows. Common scenarios include:

- Method parameter validation failures (`@NotNull`, `@Email`, `@Size`, etc.)
- Custom constraint violations
- Validation of complex domain objects passed between workflow phases

Validation occurs automatically before workflow methods are invoked when parameters
declare Jakarta Validation constraints.

[[workflow-error-handling-recovery]]
=== Error Handling and Recovery

==== Exception Handler Invocation

When an exception occurs in any workflow phase, the runtime searches for a matching
`@HandleException` method:

[source,java]
----
@Agent
public class ResilientAgent {

    @Trigger
    public void onEvent(Event event) {
        if (event == null) {
            throw new IllegalArgumentException("Event cannot be null");
        }
    }

    @Decision
    public boolean analyze(Event event) {
        // May throw IOException
        return analyzeEvent(event);
    }

    // Handles specific exception type
    @HandleException
    public void handleIOException(IOException e, Event event) {
        logger.warn("I/O error, will retry", e);
        scheduleRetry(event);
    }

    // Handles any unhandled exception
    @HandleException
    public void handleGenericException(Exception e, Event event) {
        logger.error("Unexpected error", e);
        logFailure(event, e);
    }
}
----

==== Workflow Termination

Workflows terminate in the following scenarios:

1. **Normal Completion**: Outcome phase completes successfully
2. **Decision Stops**: Decision phase returns `false` or `null`
3. **Unhandled Exception**: Exception occurs and no handler is defined
4. **Handler Exception**: Exception handler itself throws an exception
